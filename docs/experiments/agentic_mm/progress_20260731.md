## What is being built

| Part | What it is | Character |
|---|---|---|
| (1) Policy | rule-based market-making code: binary at-touch quoting plus smart cancel | the thing being optimized |
| (2) World model | frozen checkpoints: background order flow plus a forward mid curve | stochastic, learned |
| (3) Simulator | the JAX matching engine, price-time priority | **deterministic, hard-coded** |
| (4) Optimizer | `claude -p` reading PnL plus diagnostics and rewriting (1) | gradient-free; not RL, not ES |

The goal is the missing third stage of the pipeline: pretraining (autoregressive CE) → post-training (DFM/GRPO, open-loop, no market interaction) → **agentic trading (closed-loop, with market feedback)**. Four parts form the loop, and their characters must be kept strictly apart:

| Part | What it is | Character |
|---|---|---|
| ① Policy | rule-based market-making code: binary at-touch quoting + smart cancel | the thing being optimized |
| ② World model | frozen checkpoints: background order flow + a forward mid curve | stochastic, learned |
| ③ Simulator | the JAX matching engine, price-time priority | **deterministic, hard-coded** |
| ④ Optimizer | `claude -p` reading PnL plus diagnostics and rewriting ① | gradient-free; not RL, not ES |

### The causal point that must hold

The world model learns an **observational** distribution $p(\text{market})$, but market making is an **intervention**, $p(\text{market}\mid do(\text{my quotes}))$. Answering an interventional question with an observational model is optimistic in a specific direction: the generator was never trained to punish you, it will not reproduce how others react to your orders, and likelihood training tends to smooth away the unfavourable tail, so adverse selection is under-counted. **The generator must therefore never produce the fills of your own orders**; the deterministic matching engine settles those, and a real-data backtest stays the final judge.

## Key findings

### 3.1 A one-minute window costs a per-ticker constant

250 generated messages cover **0.025–0.116 s** on GOOG, not a minute. Measured from `index_2026-01.json` across 487 tickers over the full session, one minute of window costs:

| ticker | msg/s | messages per minute |
|---|---|---|
| GOOGL | 540.6 | 32,436 |
| NVDA | 420.8 | 25,246 |
| GOOG | 241.5 | 14,488 |
| KEY (median) | 7.7 | 463 |
| NVR (quietest) | 1.3 | 77 |

Quantiles of messages-per-minute: p25 = 270 · **p50 = 463** · p75 = 895 · p95 = 2,858

More than half the SP500 constituents need only a few hundred messages for a full minute, barely more than the current pipeline's 250; only the most active few percent require tens of thousands. **This is a ticker-selection decision, not a compute problem.**

### 3.2 A self-correction

I had inferred from the checkpoints' `dir_name = /lus/lfs1aip2/projects/s5e/lob_preproc` that both models were trained on GOOG only, which would have made moving to another ticker a distribution shift and forced 14,488 generated messages per minute on GOOG. Reading the `tickers` field, which actually records the corpus, refutes that: **both checkpoints were trained on the full SP500 universe (~490 tickers)**, with `data_root` mounting per-month `sp500_squashfs` shards. `dir_name` is a legacy default, not the path used. The dilemma disappears: a mid-liquidity ticker is both in distribution and affordable. Training covers 2022–2025 and evaluation is 2026-01, so the window is held out.

**Lesson: do not infer a dataset's composition from a field's name; read the field that records its contents.**

### 3.3 The J-rollout sampler needed no new code

The price curve needs J continuations of the same history to carry a distribution and a confidence. Index selection inside `runtime/inference.py` is pinned to seed 42 and is independent of `--seed` (its own comment: "Index selection stays fixed at 42"). Varying `--seed` therefore re-rolls generation randomness while leaving the conditioning windows identical, which is exactly the required sampler, with no new JAX generation code.

### 3.4 A silent-failure trap

`msg_to_lobster_format` already maps raw direction {0,1} to {-1,1} when writing the CSV, and the engine's `msg_to_jnp` reaches the same {-1,1} by computing `(d*2)-1` on the raw value. Re-applying `(d*2)-1` when reading the CSV back therefore yields {-3, 1}; the engine does not reject that, it simply matches against a side that does not exist, so the error is entirely silent. The new reader validates the column rather than trusting it.

### 3.5 Headless `claude -p` works from a compute node

There was no precedent in this repo (only `codex exec` had run inside SLURM), so this was probed rather than assumed. Job 5849614, `COMPLETED 0:0`, 10 seconds: credentials readable (567 bytes, mode 600), `api.anthropic.com` reachable (HTTP 401, i.e. network fine and auth required), `apiKeySource: none` so OAuth credentials are used, and one real call returned `PREFLIGHT_OK`. **The optimizer loop runs as a compute-node job; no login-node fallback is needed.**

Incidental finding: `--allowed-tools ""` does **not** strip the tool list (verified on the login node, where the returned list still contained Bash/Write/Edit); `--disallowed-tools` does. The script's initial "no tools are granted" comment was false and was removed rather than left in place.

## The gate that has not passed

The P0 consistency gate checks whether the CSV → engine-message → mid reconstruction is faithful, by replaying generated messages back through the matching engine and comparing against the book the generator itself recorded. Current result: 1 of 3 sequences reproduces exactly (`exact_mid` = 0.832 / 0.992 / 1.000).

### How it was diagnosed

Three hypotheses were tested; two were **refuted** rather than worked around:

| Hypothesis | Result |
|---|---|
| wrong initial state | **excluded** — `cond_book[-1]` == `gen_book[0]` == the post-reset state, value for value |
| lost queue priority, so replay the conditioning messages | **refuted** — it made things worse: 0.664 vs 0.832 |
| engine order capacity | **refuted** — `nOrders` 100 and 1050 are bit-identical |

### Root cause

The first divergence is at step 97, on a `type=3` (DELETE) message with `oid=814600586`, `qty=10`. Our top bid level holds 96 shares and the next 170, against the generator's 110 and 156: **14 shares land one level away**, and the two levels' errors cancel.

The cause is that `init_msgs_from_l2` collapses each price level of an L2 snapshot into **one synthetic order** (`INITID = -2`). But `oid=814600586` is a real order id from the conditioning window, which exists in the generator's book because it replayed the conditioning messages into it, and cannot be found in a snapshot-initialised book, so the engine's fallback removes quantity from elsewhere.

This also explains why replaying the conditioning messages made things worse: that replay starts from `condb[0]`, itself a synthetic-order snapshot, so those messages' own deletes cannot resolve either and the error compounds.

**Conclusion: this is a limitation of the archived fixture, not a defect in the new code.** That fixture stored L10 books only, while the generator ran on L500 plus conditioning replay. Stage A's own generation exports the L500 conditioning book, at which point the gate can be judged properly.

## The core architectural decision

The background order flow is **generated once offline and frozen**, after which every OPRO round is a pure CPU replay.

The justification comes from the formulation itself: it requires inference to condition only on orders that really happened, and requires the generator never to produce the fills of your own quotes. Together those make the background flow **exogenous** to the policy: it does not depend on what you quote, so it can be generated once and replayed.

That is not merely a speed trick, though it is also that (a round drops from GPU rollouts to a CPU replay measured in tens of seconds, which is what makes the loop turn at all). Two other consequences matter more: every candidate faces a **byte-identical** market, so score differences are **paired** rather than confounded by fresh sampling noise; and swapping the frozen stream for the real continuation turns the same code path into a real-data backtest with nothing else changed.

The loop still closes, and it closes at the **policy**: each step re-conditions on its own realised fills, inventory, and the post-match book. What is frozen is the market's own behaviour, not the feedback. The cost is that our own market impact is not modelled, which is a known reason simulated PnL runs optimistic; `compute_gt_divergence` exists to quantify that rather than hand-wave it.
