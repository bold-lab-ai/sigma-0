# LOBBench 为什么失败，以及我们怎样找到真正根因

> 这份文档只讲一条因果链。
>
> 每一步都依赖上一步。
>
> 如果前一步不成立，就不要继续往下猜。

## 先认识六个词

`checkpoint` 是训练后保存下来的模型。

所以，检查 checkpoint 就是在检查这个已保存模型能生成什么。

`inference` 是让模型根据输入生成新消息的过程。

所以，inference 输出就是随后交给 LOBBench 检查的数据。

`token` 是模型每一步选择的一个编号。

所以，代码还需要把 token 解码成人能理解的事件、价格和时间。

`mask` 是禁止采样某些 token 的清单。

所以，非法 token 应该先被 mask 拦住。

`replay` 是按照原来的输入和随机数重新运行一个已知坏点。

所以，replay 可以让我们看到原任务当时没有保存的中间状态。

`NaN` 表示一个无效数字。

所以，正式评分中出现 `NaN` 时，结果不能通过。

## 先看 30 秒版本

1. 我们想用 LOBBench 判断 checkpoint 的生成效果。
2. 所以，我们先让 inference 代码生成订单消息。
3. LOBBench 随后检查这些消息的统计特征。
4. 其中一个特征需要计算相邻消息的时间差。
5. 时间差必须大于或等于零。
6. 但是，生成结果里有 3 个时间差是负数。
7. 而且，这 3 个负数都正好是 `-9,999 ns`。
8. 因此，LOBBench 在对负数取对数时得到 `NaN`。
9. 因此，严格评分程序拒绝生成正式分数。
10. 这说明 inference 输出违反了时间规则。
11. 这还不能说明 checkpoint 本身效果差。
12. 当前代码证据显示，Mamba3 可能把一个非法的 `START` token 采进了时间字段。
13. CPU 实验表明，如果 `START` 进入时间字段，它就会被解码成 `-9999`。
14. CPU 实验还表明，时间累加代码会把 `-9999` 当成正常纳秒数。
15. 因此，这条路径会让时间戳恰好向后退 `9,999 ns`。
16. CPU 注入实验已经复现了这条条件因果链。
17. 但是，原始 GPU 生成没有保存当时采到的 token。
18. 所以，我们还要重放那 3 个时刻，并直接记录 token。
19. 如果重放在同一个坏消息的纳秒字段看到 `START`，我们才完成根因证明。
20. 在完成这个小实验之前，不需要重跑全部 3,136 个样本。

## 现在到底是什么状态

生成任务已经完成了全部 `3,136/3,136` 个生成窗口。

所以，当前问题不是“生成任务没有跑完”。

评分程序也已经计算了全部 `21/21` 个特征。

所以，当前问题也不是“评分程序中途没有计算”。

但是，`log_inter_arrival_time` 的两个距离指标 Wasserstein 和 KS 是 `NaN`。

所以，严格评分 gate 没有写出正式的 `lobbench_summary.json`。

因此，我们现在只有诊断结果，没有可以对外使用的正式 LOBBench 分数。

## 为什么 3 个负时间差会让评分失败

LOB 数据中的每条消息都有一个时间戳。

数据契约要求消息时间单调不减。

相同时间允许出现，所以时间差可以等于零。

时间倒退不允许出现，所以时间差不能小于零。

LOBBench 的 `log_inter_arrival_time` 会对这个差值取对数。

但是，负数没有实数范围内的对数。

所以，负时间差会产生 `NaN`。

一旦一个特征包含 `NaN`，严格评分就不能把它当成有效结果。

所以，评分程序拒绝写出正式结果是正确行为。

## 我们实际观察到了什么

每个生成窗口包含 250 条消息。

所以，每个窗口包含 249 个相邻时间差。

因此，`3,136 × 249 = 780,864`。

所以，全部生成数据一共有 `780,864` 个相邻时间差。

其中只有 3 个时间差是负数。

这 3 个负数都精确等于 `-9,999 ns`。

它们不是接近 `-9,999 ns`。

它们也不是三个不同的随机负数。

因此，这不像普通的浮点误差。

相反，`-9999` 正好是当前编码代码使用的哨兵值。

哨兵值是代码用来表示异常状态的特殊数字。

所以，调查方向从“浮点误差”转向了“特殊 token 被当成时间数值”。

三个异常样本如下。

| 数据集 index | CSV 行号 | 前一个时间戳 | 后一个时间戳 | 变化 |
|---:|---:|---:|---:|---:|
| `104519` | `194 → 195` | `35726.481285006` | `35726.481275007` | `-9,999 ns` |
| `186234` | `60 → 61` | `35464.802688956` | `35464.802678957` | `-9,999 ns` |
| `222810` | `58 → 59` | `52012.699107222` | `52012.699097223` | `-9,999 ns` |

这里使用的是从 1 开始计数的 CSV 行号。

所以，代码中的后一条消息位置分别是 `194`、`60` 和 `58`，因为代码从 0 开始计数。

## `START` token 是什么

模型不是直接输出一个完整时间戳。

模型先输出多个离散 token。

代码再把这些 token 组合成秒和纳秒。

`START` 是一个特殊 token。

它的作用是表示一段序列的开始。

所以，它不应该出现在新消息的时间数字里面。

当前代码中，`START` 的 token id 是 `3`。

当前代码还把这个特殊 token 对应到特殊值 `-30000`。

随后，`combine_field()` 看到字段中存在特殊值时，会返回 `NA_VAL=-9999`。

所以，只要 `START` 混进一个时间字段，整个字段就可能变成 `-9999`。

## Mamba3 路径为什么可疑

inference 会先建立一个 validity mask。

这个 mask 决定下一步允许采样哪些 token。

大多数特殊 token 已经被这个 mask 屏蔽。

但是，只有 `block_start_tok=True` 时，`START` 才会被屏蔽。

当前 transformer 和 NSA 路径会设置这个开关。

当前 Mamba3 路径不会设置这个开关。

所以，Mamba3 的时间字段仍然允许采到 `START`。

完整分布采样又不会只保留最高概率 token。

所以，即使 `START` 的概率很低，长时间生成时仍然可能偶尔采到它。

这与“780,864 个差分中只坏了 3 个”的稀有故障模式一致。

## `-9999` 怎样变成倒退的时间

下面五步目前是 CPU 实验已经证明的条件链。

第一步，假设模型在一个纳秒字段中采到 `START`。

第二步，`combine_field()` 把包含特殊 token 的字段解码为 `-9999`。

第三步，`_add_time_tokens()` 把这个值交给 `add_times()`。

第四步，`add_times()` 没有拒绝 sentinel，也没有拒绝负增量。

第五步，`add_times()` 直接把 `-9999` 当成纳秒增量。

因此，新时间戳比旧时间戳少了 `9,999 ns`。

CPU 注入实验已经精确复现：

```text
35726.481285006
        - 0.000009999
=35726.481275007
```

所以，这条代码链能够完整解释实际异常。

但是，我们仍要用 GPU replay 检查原任务是否真的进入了这条链。

## 为什么现在还要做一次 GPU replay

CPU 实验证明了“这条代码路径能够制造相同错误”。

但是，能够制造相同错误不等于已经看到原任务真的采到了 `START`。

原始 GPU 任务没有保存每一步采到的原始 token。

所以，原始产物只能看到最终倒退的时间戳。

为了完成直接证明，我们必须用相同 checkpoint、数据位置和随机数历史重放异常时刻。

重放时，我们会在写 CSV 之前记录原始 token。

只在任意位置看到 token id `3` 还不够。

我们必须在同一个异常消息的 `delta_t_ns` 数字位看到 token id `3`。

我们还必须同时看到 mask 允许它、解码得到 `-9999`，并复现同一个时间倒退。

只有这四件事连在一起，推测才变成直接证据。

## 下一步实验只回答一个问题

从这里开始是执行人员细节。

如果你只想知道结论，可以停在上一节。

这个问题是：

> 原始异常时刻是否真的在时间字段采到了 `START` token？

为了回答这个问题，我们只重放三个已知异常上下文。

我们暂时不重跑全部数据。

`Global position` 是该窗口在全部 3,136 个窗口中的位置。

`Rank` 是原任务中负责该窗口的 GPU 进程。

`Rank position` 是该窗口在对应 GPU 进程中的位置。

`Batch` 是该窗口所在的批次。

`Slot` 是该窗口在批次内部的位置。

`Seed` 是该 GPU 进程使用的随机种子。

所以，下面这些坐标可以恢复每个坏点原来的随机数位置。

三个 replay 目标如下。

| 异常 | Global position | Rank | Rank position | Batch | Slot | Seed |
|---:|---:|---:|---:|---:|---:|---:|
| `104519` | `1468` | `0` | `367` | `91` | `3` | `2026` |
| `186234` | `2582` | `2` | `645` | `161` | `1` | `2028` |
| `222810` | `3093` | `1` | `773` | `193` | `1` | `2027` |

## Replay 必须记录什么

Replay 先记录当前数据集 index。

这样，我们能确认自己重放的是正确样本。

Replay 再记录当前消息 step。

这样，我们能确认异常发生在样本中的正确位置。

Replay 再记录每个时间位置采到的 token id。

这样，我们能直接检查 token id `3` 是否出现。

Replay 再记录 validity mask。

这样，我们能判断代码当时是否允许采样 `START`。

Replay 再记录 `START` 的 logit、概率和排名。

logit 是模型转换成概率之前的原始分数。

这样，我们能区分“模型给了低概率”与“代码错误地允许了非法 token”。

Replay 再记录解码后的时间增量。

这样，我们能看到 token 是否被变成 `-9999`。

Replay 最后记录解码结果以及累加前后的整数秒和纳秒。

这样，我们能找到第一个非法状态究竟出现于采样、解码还是累加。

## 四组 A/B 实验怎样排除其他解释

四组实验使用相同 checkpoint、输入和随机数。

所以，它们的起点保持一致。

实验只改变两个因素。

第一个因素是 START mask 是否屏蔽 `START`。

第二个因素是 fail-fast 是否在发现非法状态时立即停止。

这里的 fail-fast 会依次检查非法 `START`、`-9999` 增量和倒退时间。

| 组别 | START mask | 时间 fail-fast | 预期结果 |
|---|---|---|---|
| A | 当前行为 | 关闭 | 复现 `START → -9999 → 时间倒退` |
| B | 所有架构都屏蔽 START | 关闭 | 不再产生负时间 |
| C | 当前行为 | 开启 | 在非法 token 写入 CSV 前停止 |
| D | 所有架构都屏蔽 START | 开启 | 三个 replay 全部通过 |

如果 A 复现倒退，而 B 在相同起始 RNG key 下不再倒退，差异就来自 START mask。

如果 C 在同一个位置先捕获非法 START，fail-fast 就确认了第一处非法状态。

如果 D 的三个反例全部通过，说明修复和防护通过了第一轮检查。

但是，D 还不能代表整体已经修好。

所以，D 之后仍然需要 128 窗口和完整回归。

因此，这四组实验先区分“模型偶尔给 START 概率”和“inference 允许非法输出”。

## 不同观察结果分别说明什么

如果 trace 显示 START 被允许并被采样，根因就是 inference mask。

如果 trace 没有特殊 token，但正常 token 被解码成 `-9999`，根因就是 token mapping 或字段索引。

如果解码后的 delta 非负，但内部时间仍然倒退，根因就是 `add_times()` 的累加或进位。

如果内部整数时间单调，但 CSV 中的时间倒退，根因就是序列化。

如果 CSV 时间完全单调，但 scorer 仍然产生 `NaN`，根因才位于 parser 或 scorer。

这套顺序保证我们不会一开始就修改错误的模块。

## 什么结果才算真正修好

第一，三个 replay 都必须找到或排除第一处非法状态。

第二，修复后的三个 replay 必须没有负时间差。

第三，128 个冻结窗口和多个 seed 必须没有负时间差。

第四，完整 3,136 个样本必须没有负时间差。

第五，21 个特征所需的全部正式统计值都必须是有限数。

第六，流程必须正常写出 `evaluation_complete.json`。

只有六项全部满足，我们才宣称 inference 修复完成。

## 哪些做法不能算修复

删除那 3 行不能算修复。

把负数强行 clamp 成零也不能算修复。

让 scorer 对 `NaN` 做 `dropna` 也不能算修复。

这些做法只会隐藏 inference 已经生成非法时间的事实。

所以，它们不能用于正式 LOBBench 结果。

## 你现在只需要记住三句话

第一，checkpoint 已经生成完数据，但 inference 输出里有 3 个非法倒退时间。

第二，最强证据指向 Mamba3 没有屏蔽时间字段中的 `START` token。

第三，下一步只重放 3 个坏点并记录 token，不先重跑全部 3,136 个样本。
